# 프로젝트 구조 규칙

> **한 줄 요약** — 기능마다 폴더 하나를 갖고, 그 폴더 밖은 건드리지 않습니다.
> 남의 코드가 필요하면 **import하지 말고 복사하세요.** 복사는 이 프로젝트에서 잘못이 아닙니다.

이 문서의 목적은 하나입니다. **내가 짠 코드가 남의 화면을 깨뜨리는 일을 없애는 것.**

---

## 왜 이렇게 하나

공용 컴포넌트를 하나 고치면 그걸 쓰는 모든 화면이 같이 바뀝니다. 문제는 그게 **몇 개인지, 어디인지 눈에 보이지 않는다**는 점입니다. 잘 돌아가는 걸 확인하고 올린 수정이 남의 화면 세 개를 깨는 일이 여기서 생깁니다.

기능별로 폴더를 나누고 복사를 허용하면, 내가 고친 코드의 영향 범위가 **폴더 이름에 적혀 있게** 됩니다. `features/movies/` 안을 고쳤다면 영향받는 건 영화 기능뿐입니다. 그 이상도 이하도 아닙니다.

성능이나 번들 크기 걱정은 하지 않아도 됩니다. 컴포넌트 몇 개 중복되는 비용보다, 화면이 깨지고 원인을 찾는 비용이 훨씬 큽니다.

---

## 폴더 구조

```
src/
├── features/          # 기능 모듈. 대부분의 코드가 여기 들어갑니다
│   └── greeting/
│       ├── components/    # 이 기능 전용 컴포넌트
│       ├── api/           # 이 기능이 호출하는 API
│       ├── hooks/         # 이 기능 전용 훅 (필요할 때 만드세요)
│       └── types.ts       # 이 기능 전용 타입
│
├── pages/             # 화면. feature들을 조합하는 유일한 장소
│   ├── HomePage.tsx       # 단순한 페이지는 파일 하나
│   └── movies/            # 파일이 2개째 필요해지면 폴더로
│       ├── MovieListPage.tsx
│       ├── MovieDetailPage.tsx
│       └── components/    # 이 라우트 전용
│
├── routes.tsx         # 라우팅 정의
│
├── lib/               # [고정] http 클라이언트, 외부 라이브러리 설정
├── types/             # [고정] 서버 응답 타입
├── styles/            # [고정] 디자인 토큰 (색상, 간격)
│
├── App.tsx
└── main.tsx
```

### `components/`, `hooks/`, `utils/` 가 최상단에 없는 이유

일부러 만들지 않았습니다. 비어 있는 공용 폴더가 있으면 사람들이 채우게 되고, 그 순간 이 구조의 의미가 사라집니다. **공용 폴더는 필요해서 만드는 게 아니라, 기술부채 기간에 팀이 합의해서 만드는 것**입니다.

## 규칙 1. feature끼리 import 금지

```ts
// ❌ 금지 — features/movies 안에서
import { LoginForm } from "@/features/auth/components/LoginForm";

// ❌ 금지 — 상대경로로 우회하는 것도 안 됩니다
import { LoginForm } from "../../auth/components/LoginForm";
```

두 기능을 같이 써야 한다면 방법은 두 가지입니다.

**방법 1 — 복사한다** (대부분 이쪽)

```ts
// features/movies/components/MovieCard.tsx
// @duplicate-of: src/features/search/components/ResultCard.tsx
```

**방법 2 — 페이지에서 조합한다**

```tsx
// pages/MoviePage.tsx — 페이지는 여러 feature를 가져다 쓸 수 있습니다
import { MovieList } from "@/features/movies/components/MovieList";
import { SearchBar } from "@/features/search/components/SearchBar";
```

이 규칙은 **린트가 자동으로 막습니다.** 어기면 `npm run lint`에서 에러가 납니다.

---

## 규칙 2. 중복은 기본값입니다

> **복사는 승인된 행동입니다. 죄책감을 가질 필요가 없습니다.**

DRY(중복을 피하라)를 배우고 오신 분들이 복사를 꺼리는데, 이 프로젝트에서는 반대입니다.

- 남의 feature에서 컴포넌트가 필요하다 → **복사**
- 비슷한 함수가 이미 있다 → **복사**
- "이거 공용으로 빼면 좋을 것 같은데?" → **하지 마세요.** 복사하고 넘어갑니다

**시키지 않은 공용화 리팩터링은 하지 않습니다.** 중복 컴포넌트 여러 개를 하나로 합치는 PR은, 그 의도가 아무리 좋아도 이 프로젝트가 막으려는 사고를 정확히 만들어냅니다.

### 복사할 때 남길 것

복사본 맨 위에 주석 한 줄:

```tsx
// @duplicate-of: src/features/greeting/components/GreetingCard.tsx
```

이유는 두 가지입니다.

1. 원본에서 버그를 고칠 때 `grep -r "@duplicate-of" src` 로 형제 복사본을 찾을 수 있습니다
2. 나중에 기술부채를 정리할 때 목록이 이미 만들어져 있습니다

**중복의 유일한 실제 비용은 "버그 수정이 복사본에 전파되지 않는 것"입니다.** 이 주석이 그걸 막아줍니다. 꼭 남겨주세요.

---

## 규칙 3. 고정 구역 3개는 복사하지 않습니다

| 폴더      | 들어가는 것                     | 복사하면 생기는 일                       |
| --------- | ------------------------------- | ---------------------------------------- |
| `styles/` | 색상 토큰                       | 화면마다 색이 미묘하게 달라짐            |
| `lib/`    | http 클라이언트, 인증 토큰 처리 | 로그아웃·토큰갱신이 일부 화면에서만 동작 |
| `types/`  | 서버 응답 타입                  | 서버가 필드를 바꿔도 타입 에러가 안 남   |

기준은 **"틀렸을 때 누가 알아채는가"** 입니다.

버튼 모서리가 두 화면에서 4px, 6px로 갈라져도 아무 일도 안 일어납니다. 그런데 할인율 계산이 장바구니와 결제 화면에서 갈라지면 **돈이 틀리는데 화면은 멀쩡합니다.** 아무도 모릅니다.

정리하면 — **생긴 것(표현)은 복사해도 되고, 사실(진실)은 복사하면 안 됩니다.**

로그인 여부 판정, 가격 계산, 유효성 검사 규칙처럼 **"답이 하나여야 하는 것"** 도 여기 해당합니다. 이런 게 필요하면 `lib/` 에 넣고 팀에 알려주세요.

## 규칙 4. 컴포넌트는 props만 받고, 데이터는 페이지가 가져옵니다

| 이름 | 하는 일 | 어디에 |
| --- | --- | --- |
| **컴포넌트 (Presenter)** | props로 받은 걸 화면에 그리기만 | `features/<기능>/components/` |
| **페이지 (Container)** | 데이터를 가져와서 컴포넌트에 넘기고, 조립 | `pages/` |

```tsx
// ❌ 컴포넌트가 직접 데이터를 가져오는 것 — 린트가 막습니다
export function MovieCard() {
  const movie = useMovie()   // 금지
  return <article>{movie.title}</article>
}

// ✅ props로 받습니다
export function MovieCard({ movie }: { movie: Movie }) {
  return <article>{movie.title}</article>
}

// ✅ 데이터는 페이지에서
export function MoviePage() {
  const movies = useMovies()
  return movies.map((m) => <MovieCard key={m.id} movie={m} />)
}
```

### 왜 이렇게 하나

**컴포넌트가 무엇을 건드리는지가 props 목록에 전부 적히게 됩니다.**

props만 받는 컴포넌트는 몰래 서버를 호출하거나 다른 데이터를 바꿀 수 없습니다. `MovieCard({ movie })` 를 보면 이 컴포넌트가 영향받는 범위가 `movie` 하나라는 걸 읽는 즉시 알 수 있죠. 이건 폴더로 영향 범위를 보이게 만든 규칙 1과 같은 목적입니다.

디버깅도 쉬워집니다. 화면에 데이터가 안 나올 때 볼 곳이 페이지 한 군데로 좁혀집니다.

### 예외 — `useState`는 써도 됩니다

금지되는 건 **데이터를 가져오는 것**이지 상태를 갖는 게 아닙니다. 열림/닫힘 토글, 입력값 같은 화면 자체의 상태는 컴포넌트 안에서 `useState`로 관리해도 됩니다.

```tsx
export function MovieCard({ movie }: MovieCardProps) {
  const [open, setOpen] = useState(false)   // ✅ 괜찮습니다
  ...
}
```

### 페이지 전용 컴포넌트는 어디에 두나요

페이지가 길어져서 컴포넌트를 파일로 빼고 싶을 때가 옵니다. 그때 **`features/`로 보내지 마세요.** 공유되는 게 아니라 그 화면 전용이니까요.

그 라우트 폴더 안에 `components/` 를 만듭니다.

```
src/pages/movies/
├── MovieListPage.tsx
└── components/
    └── MovieFilterBar.tsx
```

**폴더는 필요해질 때 만듭니다.** 페이지가 파일 하나로 충분하면 `pages/HomePage.tsx` 그대로 두세요. 그 라우트에 파일이 2개째 필요해지는 순간 폴더로 옮기면 됩니다. 미리 만들어두면 빈 폴더만 늘어납니다.

그리고 **다른 라우트가 이 `components/` 를 가져다 쓰는 건 금지**입니다. 린트가 막습니다. 필요하면 복사하고 `@duplicate-of` 주석을 남기세요 — 규칙 2와 같습니다.

### props 넘기는 게 번거로운데요

번거로운 게 맞습니다. 그리고 그게 이 규칙의 값입니다. 넘기는 게 귀찮아질 만큼 props가 늘어났다면, 그건 보통 **컴포넌트가 너무 많은 일을 하고 있다는 신호**입니다.

## import 작성법

| 대상                         | 방법      | 예시                                |
| ---------------------------- | --------- | ----------------------------------- |
| 같은 feature 안              | 상대경로  | `import { X } from '../types'`      |
| 고정 구역 (lib/types/styles) | `@/` 별칭 | `import { http } from '@/lib/http'` |
| 다른 feature                 | **금지**  | —                                   |

`../../` 처럼 두 단계 이상 올라가는 상대경로는 feature 안에서 금지입니다. 그건 폴더 밖으로 나갔다는 뜻이니까요. 린트가 막습니다.

그래서 **feature 폴더는 2단계까지만** 만듭니다. (`features/movies/components/MovieCard.tsx` ✅ / `features/movies/components/card/parts/X.tsx` ❌)

---

## 새 기능 만드는 순서

```
1. src/features/<기능이름>/ 폴더를 만든다
2. 그 안에 components/, api/, types.ts 를 필요한 만큼 만든다
3. 다른 feature 코드가 필요하면 복사하고 @duplicate-of 주석을 남긴다
4. src/pages/ 에 페이지를 만들어 feature를 연결한다
5. src/routes.tsx 에 경로를 추가한다
6. npm run lint 로 규칙 위반이 없는지 확인한다
```

`src/features/greeting/` 이 참고용 예시입니다. 그대로 복사해서 시작하세요.

## 승격(공용화)에 대하여

중복된 컴포넌트를 공용으로 올리는 것을 **승격**이라고 부릅니다.

**승격은 지양합니다.** 그리고 승격은 **별도로 잡힌 기술부채 해결 기간에만** 진행합니다.

기능 개발 중에는 어떤 경우에도 승격하지 않습니다. 중복이 몇 개가 됐든, 얼마나 똑같아 보이든 상관없습니다. 기능을 만드는 중에는 복사만 합니다.

부채 기간이 오면 그때 `@duplicate-of` 주석을 모아 팀이 함께 판단합니다. 그 시점에도 기본 방침은 **"굳이 합치지 않는다"** 입니다. 합쳐서 얻는 이득이 명확히 설명되는 것만 올립니다.

---

## 린트가 막아주는 것

`npm run lint` 로 확인합니다. 아래는 **자동으로 에러**가 납니다.

- feature → 다른 feature import
- feature → pages import
- feature 안에서 `../../` 로 폴더 밖 탈출
- lib/types/styles → features/pages import (의존 방향 역행)
- 순환 참조(circular import)

에러 메시지에 해결 방법이 같이 나옵니다. 막히면 메시지를 먼저 읽어보세요.

## 자주 묻는 것

**Q. 진짜 복사해도 되나요?**
네. 이 프로젝트에서는 복사가 정답입니다.

**Q. 똑같은 컴포넌트가 5개나 생겼는데 괜찮나요?**
괜찮습니다. 5개가 각자 다르게 바뀌고 있다면 오히려 애초에 다른 컴포넌트였다는 뜻입니다.

**Q. 공용으로 빼면 훨씬 깔끔할 것 같은데요?**
깔끔한 건 맞습니다. 그런데 그 대가로 "내 수정이 어디까지 영향 가는지 모르는 상태"를 얻게 됩니다. 이 프로젝트는 그 거래를 하지 않기로 했습니다.

**Q. 페이지에서도 복사해야 하나요?**
아니요. 페이지는 feature를 마음껏 import해도 됩니다. 조합하라고 있는 자리입니다.

**Q. 유틸 함수(날짜 포맷 같은 것)는 어디에 두나요?**
쓰는 feature 안에 둡니다. 다른 feature에도 필요하면 복사합니다.
